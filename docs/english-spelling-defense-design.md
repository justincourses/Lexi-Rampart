# 英语补词 × 塔防改进方案

## 目标

本方案将当前的三消输入替换为轻量英语补词玩法。玩家通过补全单词获得符文、补强与军功，塔防系统继续负责敌军推进、自动攻击、城墙生存和波次成长。

游戏仍然是一款塔防小游戏，不承担完整的英语教学任务。CEFR 等级只用于划分词库和控制题目难度，不引入释义、例句、课程、复习计划或学习评估。

## 设计结论

现有系统适合进行这项改造。三消棋盘主要负责产出余烬、奥能、修复、补强和军功，而战场独立消费这些资源，因此新玩法可以替换左侧输入区并保留大部分塔防反馈。

核心循环调整为：

```text
随机选择当前难度词库中的单词
  → 隐藏其中 1–3 个字母
  → 玩家按顺序点击 A–Z 补全空位
  → 答对后朗读单词并结算符文与积分
  → 错误累计 3 次后揭示答案并自动换词
  → 符文继续驱动自动攻击、技能、修复和升级
```

## 难度与词库

游戏开始时继续提供三个难度。每个难度同时选择塔防压力和参考 CEFR 分级的词库。

| 游戏难度 | 建议词库 | 主要特征 |
| --- | --- | --- |
| 萌新 | A1–A2 | 高频短词为主，通常隐藏 1 个字母 |
| 老兵 | B1–B2 | 中等长度词汇，通常隐藏 1–2 个字母 |
| 大佬 | C1–C2 | 较长或较少见的词汇，通常隐藏 2–3 个字母 |

CEFR 本身不提供唯一且穷尽的官方英语词表。界面和文档应使用“参考 CEFR 分级”之类的表述，避免将词库描述为正式的 CEFR 认证内容。

词库应随游戏静态发布，不应在每次出题时调用在线词典。静态词库可以离线运行，也能避免接口费用、网络错误和第三方返回内容不稳定等问题。

建议将词库预处理为按等级拆分的 JSON 数据：

```text
words-a1.json
words-a2.json
words-b1.json
words-b2.json
words-c1.json
words-c2.json
```

每条记录第一版只需要保存单词和等级。后续可以按需增加词频、词性或发音偏好，但这些字段不属于首版必需内容。

## 词库来源与过滤

[Words CEFR Dataset](https://github.com/Maximax67/Words-CEFR-Dataset) 可以作为候选原始数据源。该项目提供单词、词频、词性和推算出的 CEFR 等级，并以 MIT 许可证发布项目内容；其数据处理也引用 CEFR-J 等上游资源，正式发布前仍需复核上游许可和最终使用范围。

该数据集包含算法推算的分级结果，不能直接作为最终游戏词库。导入流程应至少执行以下过滤：

- 只保留由小写英文字母 `a-z` 组成的单词。
- 首版只保留长度为 3–12 的单词。
- 排除人名、地名、缩写、数字、连字符和撇号形式。
- 排除攻击性词汇和不适合公开展示的内容。
- 排除极低频、古旧或高度专业化的词汇。
- 合并明显重复的大小写、词形和数据记录。
- 从每个等级随机抽查一批单词，修正明显错误的分级。

游戏运行时应使用洗牌袋选择单词，而不是每题直接独立随机。洗牌袋可以减少短时间重复，并保证玩家在消耗一部分词库前不会反复遇到相同单词。

## 生成补词题目

系统根据单词长度、当前难度和少量随机因素决定隐藏位置。题目始终保留至少两个可见字母，避免将短词变成没有提示的完整拼写题。

| 单词长度 | 基础隐藏数量 |
| --- | --- |
| 3–4 | 1 |
| 5–7 | 1–2 |
| 8–10 | 2–3 |
| 11–12 | 3 |

难度可以在基础范围内调整随机权重。例如，萌新更常选择范围下限，大佬更常选择范围上限。随机位置不需要理解单词含义，但应避免连续多题只隐藏首字母或末尾字母。

题目示例：

```text
D _ F _ N S _
```

缺失答案依次是 `E → E → E`。系统使用原单词中的位置顺序，不要求玩家先选择要填写的空位。

## 字母输入

左侧面板显示固定的 A–Z 字母表。玩家点击或触摸字母后，系统尝试将它填入当前最左侧的未完成空位。

- 正确字母进入空位并保持锁定。
- 错误字母不进入空位，单词和字母按钮显示短暂的错误反馈。
- 已经填对的字母不会因为后续错误而清空。
- 实体键盘的 `A–Z` 键可以触发相同输入，提升桌面端操作速度。
- 输入锁只覆盖短暂的正确、错误和换题动画，不应长时间阻断操作。

点击或触摸应作为首版主操作。拖放可以作为后续可选交互，但它会增加移动端误触、重复字母处理和无障碍操作的复杂度，不应成为完成首版的前置条件。

## 错误与自动跳过

每个单词独立记录错误次数。错误次数统计错误的字母输入，而不是整词提交次数。

| 错误次数 | 行为 |
| --- | --- |
| 1 | 错误反馈，继续当前单词 |
| 2 | 更明显的警告，继续当前单词 |
| 3 | 揭示完整单词，短暂停留后自动换题 |

第三次错误后，系统应显示完整答案约 0.8–1.2 秒，然后自动进入下一个单词。跳过不会清空已经获得的资源，也不会额外伤害城墙，但本题不提供符文或积分。

首版不需要单独的免费跳过按钮。免费跳过会鼓励玩家不断刷新题目以寻找更短的单词或特定符文奖励。如果后续增加主动跳过，它应视为本题失败，并使用与三次错误相同的结算方式。

## 符文与积分

奖励系统将“符文类型”和“奖励价值”分开计算：

- 符文类型使用受控随机。
- 符文数量和积分主要由题目挑战度决定。
- 少量随机浮动负责制造惊喜，但不应盖过难度因素。

题目挑战度可以使用以下因素：

```text
挑战度 = CEFR 等级权重 + 单词长度权重 + 隐藏字母数量权重
```

建议的基础奖励区间如下：

| 题目特征 | 基础符文 |
| --- | --- |
| 短词、隐藏 1 个字母 | 1 枚 |
| 中等长度或隐藏 2 个字母 | 2 枚 |
| 高等级长词且隐藏 3 个字母 | 3 枚 |

正确率继续调整最终奖励：

| 本题错误 | 奖励建议 |
| --- | --- |
| 0 | 100% 奖励，并提供首次正确加分 |
| 1 | 75%–85% 积分，保留主要符文奖励 |
| 2 | 40%–60% 积分，降低符文奖励 |
| 3 | 自动跳过，不提供奖励 |

分数用于战报和排行榜，不直接影响战斗。符文继续映射到现有资源：

- 红曜石提供余烬攻击增益。
- 蓝晶积累奥能并释放全场攻击。
- 绿晶修复城墙或补充护盾。
- 铸币提供补强并推动军械升级。

### 受控随机

符文类型不应使用四种类型各自独立的纯随机。系统可以将余烬、奥能、修复和补强装入一个符文袋，打乱后依次抽取，抽空后再重新装袋。

符文袋保留随机感，同时防止玩家连续完成大量单词却始终拿不到修复或补强资源。题目出现时可以提前展示基础奖励，例如“本题：蓝晶 ×2”，让玩家理解补词与战斗之间的关系。

## 单词朗读

答对后朗读完整单词可以作为成功音效。浏览器提供的 [`SpeechSynthesisUtterance`](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesisUtterance) 已在主流浏览器中广泛可用，首版不需要语音服务器或预录音频。

朗读功能应遵循以下规则：

- 优先选择 `en-US` 或 `en-GB` 的系统语音。
- 使用略慢于正常语速的播放速度。
- 播放新单词前取消仍在队列中的旧朗读，避免连续答题后产生语音积压。
- 将朗读音量和开关接入现有战斗音效设置。
- 浏览器没有英文语音或朗读失败时保持静默，不影响换题和奖励结算。

系统语音的音质和口音会随设备变化，但它适合作为非关键的成功反馈。如果未来要求所有设备使用一致的真人发音，再评估预录音频或词典语音 API。

## 塔防节奏

敌军、自动弩炮和波次在玩家补词时继续运行。补词不应暂停整个战场，否则玩家可以通过停留在单词上无限冻结敌军。

现有的“本波建议消除组数”应调整为“本波建议完成单词数”。平衡模型也应从预期每波消除次数改为预期每分钟完成单词数，并同时考虑三个因素：

- 当前词库等级。
- 平均隐藏字母数量。
- 玩家发生错误和自动跳过的比例。

萌新难度需要给玩家足够时间观察字母表。老兵和大佬可以通过更高敌军压力、更多隐藏字母和更高等级词库共同提升挑战，但不应依靠很短的单题倒计时制造压力。

## 界面调整

左侧“符文工坊”区域可以保留现有视觉主题，并将棋盘替换为以下组件：

1. 当前词库与难度标识。
2. 当前补词题目。
3. 三次错误指示器。
4. 本题预计符文奖励。
5. A–Z 字母表。
6. 简短的正确、错误、揭示答案和换题动画。

现有资源栏、战场、军情日志、装备升级、城墙状态和波次显示可以继续使用。连锁标识可以改为“连续答对”，但连续答对只增加分数或视觉表现，不应成为获得基本生存资源的必要条件。

## 状态与存档

新玩法需要保存以下最小状态：

- 当前难度和词库等级。
- 当前单词。
- 当前隐藏位置与已经填入的字母。
- 当前单词的错误次数。
- 单词洗牌袋的剩余位置或等价随机状态。
- 当前题目的符文奖励。

存档仍需保留现有战斗、波次、敌军、资源和装备状态。替换棋盘状态会改变持久化结构，因此正式改造时需要提升存档版本，并为旧版三消存档提供明确的归档或迁移策略。

测试钩子 `window.__runeRampartTest` 和现有 `localStorage` key 不应随意改名。测试可以增加当前单词、隐藏位置、错误次数和强制换题等公开字段，但应保留已有战斗测试能力。

## 模块影响

改造主要发生在输入与奖励生产侧，战斗消费侧保持稳定。

| 模块 | 影响 |
| --- | --- |
| `board.js`、`board-flow.js`、`match-logic.js` | 三消流程不再作为主玩法，需要由补词逻辑替代 |
| `events.js` | 将棋盘交换事件替换为字母点击、触摸和键盘输入 |
| `state.js` | 将棋盘状态替换为当前单词、空位、错误和词袋状态 |
| `save.js` | 升级存档形状并处理旧战局 |
| `hud.js`、`ui.js` | 将消除、连锁和建议组数文案替换为补词指标 |
| `combat-math.js` | 使用完成单词速度重新校准每波资源产量 |
| `combat.js`、`combat-stats.js` | 继续负责敌军、攻击和资源消费，原则上只需少量适配 |
| `audio.js` | 增加可降级的系统语音朗读入口 |
| `runtime.js` | 按现有 `attachX()` 约定组装新的补词模块 |

新逻辑仍应遵循领域模块边界。词库加载、纯补词规则、界面渲染和奖励桥接应分开组织，不应全部堆入 `runtime.js`。

## 首版范围

首版只需要验证补词输入能否与实时塔防节奏结合：

- 使用三个难度和三个对应词库区间。
- 每题隐藏 1–3 个字母。
- 支持点击、触摸和实体键盘输入。
- 累计三次错误后自动揭示并换题。
- 答对后尝试朗读单词。
- 根据难度、长度、隐藏数量和少量随机因素结算符文与积分。
- 保留现有塔防、资源、装备、波次和本地战报。

首版不包含释义、例句、账号、云存档、复习算法、学习报告、发音评分或在线词典请求。这些功能不会影响核心玩法是否成立，因此不应阻塞原型验证。

## 验证重点

原型需要回答以下问题：

- 玩家能否快速理解“按顺序填空”的规则。
- 三次错误自动跳过是否足以避免卡关。
- 字母表输入速度能否跟上敌军压力。
- 长词和高等级词的奖励是否明显但不过强。
- 受控随机能否避免关键符文长期断供。
- 系统朗读是否会与战斗音效冲突或产生播放队列。
- 玩家是否愿意为了继续守城连续完成更多单词。

如果这些问题得到正面结果，补词玩法就可以作为三消输入的完整替代方案继续开发；否则仍可以保留塔防系统，并调整缺字数量、奖励强度或敌军速度，而不需要重写战斗核心。
